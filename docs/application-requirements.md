# 注文管理アプリケーションの前提要件

## 1. 目的

Customer Ordersサンプルスキーマを業務画面から確認・更新できる、ワークショップ用の注文管理Webアプリケーションを提供する。

参加者が環境構築ではなくGitHub Copilotによる既存システムの理解、文書化、変更設計、実装、レビュー、テストに集中できることを優先する。

## 2. 想定利用者

- 注文状況を確認する受注担当者
- 在庫と出荷状況を確認する店舗・物流担当者
- 既存コードを調査・改修するワークショップ参加者

本アプリケーションはローカルの教材環境だけで利用する。インターネットや社内ネットワークへ公開する業務システムは想定しない。

## 3. 標準機能

| 機能 | 要件 |
|---|---|
| 表示言語 | 日本語と英語を切り替えられる。初回表示は日本語とし、選択した言語をブラウザーに保存する |
| ダッシュボード | 注文件数、未処理注文件数、注文金額、顧客数、商品数、直近注文、低在庫を表示する |
| 注文一覧 | 注文番号、顧客、日時、状態、合計、商品を表示し、注文状態とキーワードで絞り込む |
| 注文詳細 | 顧客、店舗、明細、数量、金額、出荷割当、状態を表示する |
| 注文登録 | 顧客、店舗、商品数量を指定して注文を登録する |
| 注文状態更新 | 定義済みの状態遷移に従って注文状態を更新する |
| 顧客一覧 | 顧客情報、注文件数、注文金額を表示する |
| 商品一覧 | 価格、全店舗在庫、JSONに保存された色・レビュー集計を表示する |
| 在庫一覧 | 店舗別・商品別の在庫数量を表示し、10個以下を低在庫として示す |
| 出荷一覧 | 出荷状態、顧客、店舗、配送先、割当明細数を表示する |
| 店舗一覧 | オンライン／実店舗の情報、注文件数、在庫数量を表示する |
| ヘルスチェック | SQLiteの簡易整合性検査結果をJSONで返す |

## 4. 業務ルール

- 新規注文の初期状態は`OPEN`とする。
- 注文には1種類以上の商品を含める。
- 商品価格は画面から受け取らず、登録時点の`products.unit_price`を注文明細へ複写する。
- 選択店舗の在庫が注文数量を満たす場合だけ登録する。
- 注文登録と在庫引当は1トランザクションで実行する。
- 未出荷の注文をキャンセルした場合は引当済み在庫を戻す。
- 注文状態は次の順序でのみ変更できる。

```text
OPEN -> PAID | CANCELLED
PAID -> SHIPPED | CANCELLED | REFUNDED
SHIPPED -> COMPLETE | REFUNDED
COMPLETE -> REFUNDED
CANCELLED / REFUNDED -> no transition
```

## 5. 技術要件

- Node.js 22.13以降を使用する。Node.js 24 LTSを推奨する。
- `node:http`、`node:sqlite`などNode.js標準機能だけを使用する。
- SQLite CLI、コンテナー、コンパイラー、外部npmパッケージを必須にしない。
- macOS、Windows、Linuxで同じnpmコマンドを使用する。
- サーバー描画HTMLと通常のHTMLフォームを使用し、フロントエンドのビルド工程を設けない。
- SQLはプレースホルダーでパラメーター化し、画面出力はHTMLエスケープする。
- アプリケーションは既定で`127.0.0.1`だけをリッスンする。

## 6. 教材として残す改修余地

次の特性は、GitHub Copilotで既存システムを理解・改善する演習に利用する。

- 手書きのルーティングとサーバー描画を持つ小規模なモノリスである。
- データアクセスと一部の業務ルールが同じモジュールに置かれている。
- 同期SQLite APIを使用し、単一プロセスで動作する。
- 認証・認可、CSRF対策、監査ログ、ページングは実装しない。
- Oracle SQL／PL/SQLの実行経路は実装せず、SQLite版と責務を分離する。
- 送料および一定金額以上の送料無料ルールは初期実装に含めず、変更設計・実装演習の候補として残す。

これらはローカル教材としての制約であり、そのまま本番公開する設計ではない。
